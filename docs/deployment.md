# Deployment

## Direct IPv6 deployment with deSEC

The production hostname is `tryknowledgebase.blaqc.space`. The deployment uses a direct public IPv6 address, deSEC authoritative DNS, Caddy automatic HTTPS, and the Docker Compose stack on one Ubuntu machine. Caddy requires externally reachable ports 80 and 443 for the HTTP challenge/TLS-ALPN challenge and automatic certificate renewal. Keep Caddy's `/data` volume persistent.

After delegating `blaqc.space` to deSEC, create a least-privilege API token with a default deny RRset policy and one allow policy for `domain=blaqc.space`, `subname=tryknowledgebase`, `type=AAAA`. The token must not be committed. Install the persistent updater from the repository with `sudo ./deployment/install-desec-ipv6-updater.sh`; it stores the token in `/etc/know/desec-ipv6.env` with mode 0600 and enables a systemd timer that runs at boot and every five minutes. Check it with `systemctl status know-desec-ipv6-update.timer` and `journalctl -u know-desec-ipv6-update.service`.

Prefer the wired server interface for the router's IPv6 firewall rule. Router-side work is manual: reserve or otherwise keep the server's IPv6 reachable, allow inbound TCP 80 and 443 to the server, and ensure the router permits IPv6 forwarding/input for those ports. Also allow the server's SSH port before tightening the host firewall. Verify externally from an IPv6-capable network with `dig AAAA tryknowledgebase.blaqc.space`, `curl -6 -I http://tryknowledgebase.blaqc.space`, and `curl -6 -I https://tryknowledgebase.blaqc.space`. IPv6-only publishing will not serve IPv4-only clients.

On Ubuntu, install Docker and point the domain's A/AAAA records at the server. Copy `.env.example` to an untracked `.env`, set a random `JWT_SECRET` and strong `POSTGRES_PASSWORD` (neither has a fallback secret), `DOMAIN`, and replace the extension-ID placeholder in `CORS_ORIGINS` with the trusted unpacked/installed extension ID. After DNS resolves, run `set -a; source .env; set +a; ./deployment/preflight.sh`, then `docker compose up -d --build`. The preflight rejects placeholder secrets, local/example domains, missing production CORS origin, unresolved DNS, invalid Compose interpolation, and invalid Caddy configuration. Compose passes `DOMAIN` into Caddy; when it is omitted for local development, Caddy listens on its local `:80` fallback. Requests for a non-local configured domain on port 80 are redirected to HTTPS; the `localhost` fallback remains available for local development and smoke tests. The convenience HTTP port 3000 is bound to loopback only for local access; only ports 80 and 443 are publicly published. The default CORS policy allows only the local web client; extension origins must be opted in through configuration. The production web build uses the same-origin `/api/v1` proxy by default; `VITE_API_URL` is only needed for a separately hosted API. To enable Google sign-in, set `GOOGLE_CLIENT_ID` to the OAuth 2.0 Web client ID configured for the deployed domain; the same value is used to verify Google ID-token audiences on the API and render the web sign-in button. Leave it blank to disable that optional button. Caddy obtains and renews certificates automatically. PostgreSQL and the API remain private.

The API exposes `/actuator/health`, and Compose waits for PostgreSQL health before starting it. The public Caddy proxy has its own HTTPS health check and emits baseline `nosniff`, frame-denial, strict-origin referrer, CSP, and restrictive Permissions-Policy headers. Compose keeps each service's JSON logs bounded to three 10 MB files; inspect them with `docker compose logs --tail=200 api` (or `db`, `web`, or `proxy`) and forward them to the host's normal log collection if required. Back up with `./deployment/backup.sh` (or pass an explicit output filename); the script refuses to overwrite an existing file. Restore into a separate database first with `psql` and verify the migration/data contents before relying on a backup. Keep the named database volume and Caddy data volume on persistent storage.

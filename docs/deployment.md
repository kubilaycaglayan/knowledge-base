# Deployment

For production, use Cloudflare Tunnel so the Ubuntu server makes only outbound connections and the router needs no inbound port rules. Add `blaqc.space` to Cloudflare, use Cloudflare nameservers (full setup), and publish `tryknowledgebase.blaqc.space` through a named tunnel to `http://proxy:80`. Copy the tunnel token into the untracked `.env` as `CLOUDFLARE_TUNNEL_TOKEN`; never commit it. Then run `set -a; source .env; set +a; COMPOSE_PROJECT_NAME=knowledge-base ./deployment/preflight.sh` followed by `./scripts/rebuild.sh`. Development uses a separate `knowledge-base-dev` Compose project and database volume. Production uses `docker-compose.production.yml` and `docker-compose.cloudflare.yml`; the production database volume is external and cannot be removed by Compose. The preflight rejects placeholder secrets, local/example domains, missing production CORS origin, missing tunnel token, missing production database volume, unresolved DNS, invalid Compose interpolation, and invalid Caddy configuration. Cloudflare terminates public HTTPS; the local Caddy origin listens only on the private Docker network. The production web build uses the same-origin `/api/v1` proxy by default. PostgreSQL, the API, Caddy, and the tunnel origin remain private.

The API exposes `/actuator/health`, and Compose waits for PostgreSQL health before starting it. The public Caddy proxy has its own HTTPS health check and emits baseline `nosniff`, frame-denial, strict-origin referrer, CSP, and restrictive Permissions-Policy headers. Compose keeps each service's JSON logs bounded to three 10 MB files; inspect them with `docker compose logs --tail=200 api` (or `db`, `web`, or `proxy`) and forward them to the host's normal log collection if required. Back up with `./deployment/backup.sh` (or pass an explicit output filename); the script refuses to overwrite an existing file. Restore into a separate database first with `psql` and verify the migration/data contents before relying on a backup. The production database volume is external and must never be removed, reset, or included in cleanup; only a deliberate backup/restore migration may replace it. Keep the production database volume and Caddy data volume on persistent storage.

# API

Bearer tokens remain valid across API restarts with the same `JWT_SECRET`, until
their existing 30-day expiry. Error dispatches preserve the original HTTP status
(such as 404 or 503), rather than returning a misleading 401. Clients should
retain credentials on network/server errors; a 401 for the current token requires
sign-in. The web client ignores a delayed 401 for a token that has been replaced.

Web light/dark preference is local presentation state (`knowledge-base-theme` in
browser storage). It adds no endpoint or account field; existing API requests,
ownership checks, and timer behavior are unchanged.

The API is rooted at `/api/v1`. Public endpoints are `POST /auth/register`, `POST /auth/login`, and `POST /auth/google`, returning a bearer JWT. Google login accepts a Google Identity Services ID token; the API verifies its signature, audience, issuer, and verified email before linking or creating the account. Clients send `Authorization: Bearer <token>`.

Interactive OpenAPI documentation is available at `/swagger-ui.html` during development; the machine-readable contract is at `/v3/api-docs`. Both endpoints are disabled in the production Spring profile.

The native iOS client uses the same authentication contracts. Google Sign-In's
`GIDServerClientID` must match backend `GOOGLE_CLIENT_ID` (the web OAuth client),
while `GIDClientID` identifies the iOS OAuth client. The app exchanges the Google
ID token for the backend JWT and saves the application session in Keychain.
See [iOS setup and smoke checks](../ios/README.md).

Authenticated endpoints currently include:

- `GET /auth/me` returns the signed-in account’s email and available sign-in methods. `PUT /auth/password` sets a first password for a Google-only account, or changes an existing password only when the correct current password is supplied. A Google-only account without a configured password may set one without a current password; Google sign-in remains linked and usable afterward. Passwords must be at least 9 characters; the password-configuration state is stored explicitly so new Google-only accounts’ random unusable hashes cannot be mistaken for usable passwords.

- `GET/POST /paths`, `GET/PUT/DELETE /paths/{id}`, and `POST /paths/{id}/restore`; path responses include a backend-computed `activityLabel` (`today`, `this week`, `this month`, or `passive`) based on the owner’s most recent recorded session. Delete is a soft delete that records `deleted_at`, removes the path from normal API results, and preserves its historical database references. Restore is owner-scoped and clears the marker so the path and all preserved relationships are available again.
- `POST /paths/{id}/merge` accepts `{ "targetPathId": "<owned-path-uuid>" }`. It atomically moves every source-path session to the separately owned target path, then soft-deletes the source. A path cannot be merged into itself, and both path IDs are ownership-checked.
- Archived paths remain readable for history but cannot receive new time entries.
- `GET /paths/{id}/summary` returns accumulated tracked seconds (including a running timer) and recent path activity. Session-backed activity includes its `timeEntryId` so clients can open the corresponding session editor.
- `GET/POST /notes`, `GET /notes/{id}`, `PUT/DELETE /notes/{id}`, `POST /notes/{id}/restore`, and `GET /notes/labels`. Notes accept one optional `pathId`, `activityId`, or `timeEntryId` target, or can be standalone. Requests with `page`/`size` return paginated notes (default size 20), and `q` searches title plus the plain-text rich-body projection. `archived=true` returns the owner’s archived notes instead of active notes. `DELETE` archives a note, and restore is available for 30 days; a scheduled UTC cleanup permanently removes older archived notes. Note bodies are Tiptap JSON serialized in `content`, with `contentText` used for excerpts/search. Note labels are user-owned reusable labels with the `NOTE` scope and are created automatically when attached to a note. Updates accept a `version` for optimistic concurrency and return HTTP 409 when another window has saved first.

  The native iOS Notes client uses the same endpoints. It serializes editable
  paragraphs as Tiptap-compatible `doc`/`paragraph`/`text` JSON, sends the
  plain-text projection, debounces saves, and replays a local draft against
  the latest version after a 409 response.
- `GET/POST /logs`, `GET /logs/{id}`, `PUT /logs/{id}`, `PUT /logs/{id}/labels`, and `DELETE /logs/{id}` manage owner-scoped, untitled text logs. Log responses include `labelIds`; `PUT /logs/{id}/labels` accepts `{ "labelIds": ["<uuid>"] }` and replaces the log’s assignments. Every assigned label must be owned by the user and have the `LOG` scope. `GET /labels?scope=LOG` returns the user’s available log labels. Log creation requires the client’s timestamp (`occurredAt`, normally the browser’s current time); records are returned newest-first by that timestamp. Updates accept an optional `version` for optimistic concurrency and return HTTP 409 when another window has saved first. Deletes require an owner-scoped lookup and permanently remove the log.
- `GET/POST/PUT/DELETE /labels` manages the unified label catalog. Labels have a nullable color and zero or more availability scopes: `NOTE`, `CALENDAR`, `TIME_ENTRY`, or `LOG`. The web and iOS label editors present these as inverse “Don’t show in” selections; new labels are hidden from Calendar by default. `GET /labels?scope=TIME_ENTRY` returns labels available to sessions; the calendar, notes, and logs endpoints expose their scoped compatibility views. A label cannot have a scope removed while it is assigned in that context. Deleting a label with assignments first returns a conflict; after explicit confirmation, `DELETE /labels/{id}?removeAssignments=true` removes only its assignment rows and the label, preserving the assigned notes, sessions, calendar records, and logs.
- `GET /timers/current`, `POST /timers`, `PUT /timers/{id}`, `POST /timers/stop`, `POST /timers/cancel`, and `POST /time-entries` accept an optional active path and zero or more owned `labelIds`. `PUT /timers/{id}` edits the start time, path, labels, and description of the owned running timer; an optional end time stops it at that time and records the resulting duration. Stopping a timer before 2 seconds discards it without recording a session; cancellation always removes an active timer without recording time.
- `GET /ws/timers` is an authenticated native WebSocket transport for timer state changes. The client sends `{"type":"AUTH","token":"<bearer-jwt>"}` as its first message, receives `READY`, and then receives `TIMER_STATE` messages containing the complete timer snapshot (or `timer: null` when it stops or is cancelled). REST remains authoritative; clients reconnect and call `/timers/current` after disconnect, app resume, or when using a legacy client. The Chrome extension currently uses the REST fallback.
- `GET /time-entries` lists owned history by completion time descending (the most recently completed session first; running sessions without a completion time follow completed sessions), `GET /time-entries/{id}` returns one owned session, `PUT /time-entries/{id}` edits completed entries, and `DELETE /time-entries/{id}` soft-deletes a completed session while preserving its database history.
- `GET /statistics` for tracked seconds and current-day and rolling-week path/label aggregates.
- `GET /reports?period=WEEK|MONTH|YEAR&anchor=YYYY-MM-DD` for a day-by-day report with total time and path/session-label categories for the selected period. Pass both `startDate=YYYY-MM-DD` and `endDate=YYYY-MM-DD` instead to request a custom inclusive range of at most two years; custom ranges also accept `aggregation=DAY|WEEK|MONTH|QUARTER|YEAR` (default `DAY`) independently of the interval. Both forms accept repeated `pathId` and `labelId` filters; selected paths are combined with selected labels (OR within each filter, AND between filters). The `sankey` response uses that aggregation for its chronological columns and links each column to the next, matching the same path before distributing remaining flow by duration. Calendar weeks start Monday in UTC, and calendar months, quarters, and years use their natural boundaries.
- `GET/POST /calendar/labels`, `PUT/DELETE /calendar/labels/{id}`, and `GET /calendar/days?startDate=YYYY-MM-DD&endDate=YYYY-MM-DD`. Labels use one of ten fixed palette colors. `PUT /calendar/days/{date}` replaces one selected day’s optional note and labels. `PUT /calendar/days/range` applies labels (and an optional note) across an inclusive range while preserving other labels already recorded on each day. A label may be a marker or carry a quarter-, half-, three-quarter-, or full-day portion. Calendar records are optional annotations and report separately from tracked work time. Labels used by historical records cannot be deleted.
- `GET /search?q=...` searches owned paths, note title/content, and recent activity.
- `GET /imports/knowledge-base/export` and `POST /imports/knowledge-base` transfer a portable CSV of owned Knowledge Base data. Path colors, label colors, label scopes, and all session, note, calendar, and log label assignments are included; log rows preserve their body and occurrence/creation timestamps. Older exports without color fields or log rows continue to import using the entity defaults. Existing records with the same stable IDs are skipped. Knowledge Base batch undo also removes imported logs and returns `deletedLogs`.
- `GET /activities` accepts optional `from`, `to`, `pathId`, and `type` filters.
- `POST /imports/clockify` accepts a Clockify export’s `timeentries` array, maps `projectName` values to owned paths (creating missing paths), stores completed entries as `IMPORT`, records an import batch, and skips already imported `_id` values. `GET /imports/clockify/batches` lists recent owned batches, including legacy imported entries backfilled during migration, and `DELETE /imports/clockify/batches/{id}` undoes the imported time entries and activity records for that batch. The Chrome extension uses this same endpoint when a detailed Clockify report response is observed.

All resource lookups are scoped by the authenticated user. A user can have at most one running timer, enforced by both a service check and a PostgreSQL partial unique index.

Unauthenticated or invalid bearer requests receive HTTP 401; authenticated users attempting to reference another user’s resources receive a resource-not-found response rather than cross-user data.
